# Plan: v0.3.0 — Agent interface

- **Status:** Implemented in v0.3.0 (2026-10-21). Section 15 lists where the build differs from this plan.
- **Date:** 2026-10-21
- **Scope:** Let an LLM agent work inside a user's Barloom workspace to help develop, evaluate, manage, and deploy cells, designed so that it stays safe once Barloom can trade a real account.

## 1. Goal and non-goals

**Goal.** Barloom works with AI in two ways, both built on one tool layer with one permission model:

- **A. The Barloom assistant.** A chat panel inside the dashboard, connected to the user's own Claude or OpenAI model. The model is reached through an API key, or through the user's subscription via that provider's official agent runtime (section 3a).
- **B. External agents.** Claude Code, Claude Desktop, or the Codex CLI connects to Barloom from outside over the Model Context Protocol (MCP).

**Providers in v0.3.0: Anthropic (Claude) and OpenAI only.** Other providers, local models, and other MCP clients are out of scope for now. The adapter design (section 3a) keeps adding them later a contained change.

**Every agent feature is disabled by default** and stays off until the user enables it and accepts the notice in section 3b.

Either way, the agent can:

- read the workspace: cells, scripts, scenarios, results, Feed experiments, and the handbook;
- write strategy scripts and cell drafts;
- run simulations (Static, suites, scenario generation, Feed Advance) and interpret the results;
- propose changes to anything that matters (Feed deployment, archiving, and later live trading), which the user approves in the Barloom app.

**Non-goals for v0.3.0.**

- **Real broker orders.** Barloom does not send any today. v0.3.0 does not add them, but it defines the permission tier and approval path they will use (section 9).
- **Barloom handling subscription logins.** Barloom never implements its own sign-in for a provider's consumer plan, and never reads or stores a plan's tokens. Subscription access goes only through the provider's own official runtime, which signs the user in itself (section 3a).
- **Hosted or multi-user access.** Barloom stays local and loopback-only.

## 2. Principles

1. **The agent is another client of the existing API, not a second engine.** Every agent action goes through the same `Api` methods, job queue, and validation as the UI. The agent cannot do anything the UI cannot.
2. **Capabilities are granted by risk tier, and consequences need a human.** Reading and simulating are cheap and reversible, so the agent does them freely. Anything that commits capital, or changes what runs unattended, is a proposal the user approves in the app, outside the agent's channel.
3. **Barloom enforces the limits; the agent cannot change them.** Grants, risk limits, and approvals live in files and endpoints that the agent's tools cannot write.
4. **Assume the agent can be wrong or manipulated.** Prompt injection can arrive through any text the agent reads: scenario descriptions, cell names, script comments, imported CSV headers, or, later, news feeds. A manipulated agent must not be able to do anything outside its grant.
5. **Everything is attributable and reversible where possible.** Every agent call is logged with its session. Cell changes already create versions, and the agent's script edits are content-addressed (ADR-0005), so they can be restored.
6. **Outputs are designed for a model's context window.** Results come as compact, structured summaries with caveats, with full detail available on request.

## 3. Architecture

```
 B. External agent (Claude Code / Desktop / any MCP client)
        │ MCP over stdio
        ▼
   barloom mcp ───────────────┐
                              │ agent token
 A. Barloom assistant         ▼
   chat panel ──▶ barloom serve: tool layer ──▶ Api v1, one job worker
   (browser)       │  grants, budgets, audit,      │
                   │  proposals, sandbox           ▼
                   │                      workspace files and SQLite
                   ├─ direct connections: Barloom runs the agent loop and
                   │  calls the model API (Anthropic or OpenAI)
                   └─ bridge connections: the provider's runtime runs the
                      loop under the user's plan and calls Barloom's tools
                      through barloom mcp
```

**The tool layer is the product; the two ways in are clients of it.** Tool definitions, grants, budgets, the audit log, proposals, and the sandbox are implemented once, in the server. `barloom mcp` exposes them over MCP. The assistant uses them in-process for direct connections, and through MCP for bridges. A capability added to the tool layer appears in both A and B with no further work.

**Decision: `barloom mcp` is a thin MCP server that forwards to a running `barloom serve`.**

- **Why not open the workspace in-process?** That would create a second job worker writing the same SQLite databases, and the app would not see the agent's jobs. One server keeps a single writer, a single job queue, and a single audit trail.
- **Starting the server.** If no server is running for the workspace, `barloom mcp` starts one in the background. To find it, the server writes `.barloom/server.json` (port, pid, start time) and removes it on exit; the Windows liveness check from c7f6a17 validates it.
- **Agent tokens.** The browser's per-process write token is not reused. The user creates an agent connection in the app (Agents → Connections), which issues a token bound to a grant (section 5). The token is shown once in the app; Barloom stores only its SHA-256 in `.barloom/agents.json` and never logs it. The user gives it to `barloom mcp` through an environment variable in the client's configuration. The Host check, loopback binding, and same-origin rules for the browser stay as they are. Agent requests authenticate with `Authorization: Bearer`, which a website cannot send cross-origin without a CORS preflight, and the server allows none.
- **Transport.** stdio MCP first, because every major client supports it. Streamable HTTP MCP on loopback can follow for clients that need it, using the same tokens.

## 3a. The Barloom assistant and model connections

**Off by default.** A fresh clone runs with no assistant, no connections, and no outbound network calls. Section 3b covers how agent features are enabled. Barloom has no telemetry and no Barloom-run service. Conversation data goes only to the provider the user chose, and only while agent features are on. Turning them off stops every connection and bridge.

**The panel.** A chat panel docks on every page and can be collapsed.

- It knows the current page and selection, so a request like "why did this cell lose in March?" works without naming the cell.
- Replies can embed live Barloom components: cell cards, metric tables, and price charts with trade markers. Tools return references (cell id, job id, chart range), and the panel renders them with the existing components instead of the model drawing them.
- Jobs the assistant starts appear in the usual job indicator and Activity.
- Proposals appear as cards that link to the Inbox. They have no approve button in the chat (section 6).
- Conversations are stored in `.barloom/chats/` and can be resumed, renamed, or deleted. Token use and cost are shown for each conversation, where the provider reports them.

**Agents → Connections** lists the model connections, each with its own grant (section 5). The assistant uses the connection chosen in the panel. Connection kinds:

| Kind | Examples | Who runs the agent loop | Credentials |
| --- | --- | --- | --- |
| Direct: API key | Anthropic API, OpenAI API | Barloom | API key in the OS keychain, or named by an environment variable; never in workspace files, logs, or responses |
| Bridge: subscription | ChatGPT plan through the Codex app server; later, a Claude plan through the user's installed Claude Code | The provider's runtime, started by Barloom on this machine | Held by the provider's runtime, which runs its own sign-in; Barloom never sees them |

**Direct connections** use two adapters: the Anthropic Messages API and the OpenAI API. Each adapter translates tool schemas, streaming, and tool calls into one internal event stream that the panel renders. Other providers and local models are deferred. When they come, an OpenAI-compatible adapter covers most of them.

**Bridge connections** start the provider's runtime as a subprocess, point it at `barloom mcp` with a bridge token, and translate its streamed events (messages, tool calls, results) into the same event stream. Each bridge is a separate, optional adapter, behind a feature flag, so one can be withdrawn if a provider changes its terms without affecting the others. Being opt-in, local, and open source settles the data-custody question, because the user's data never passes through anyone but the user and their provider. It does not settle the provider-terms question: those terms bind the user's own account, and a breach can get it suspended. OpenClaw, an open-source local tool, lost subscription access in 2026. Bridges therefore drive only the provider's official runtime, and Barloom never offers its own subscription sign-in, even as an option. Before a bridge ships, check the provider's current terms for that exact use:

- **Codex (v0.3.0).** OpenAI documents the Codex app server as the interface for other clients, and it includes Sign in with ChatGPT. This is the first bridge, and the maintainer will test it with a ChatGPT subscription.
- **Claude Code (after v0.3.0, once confirmed).** Anthropic's consumer terms forbid third-party products from using subscription OAuth tokens. Barloom would only start the user's own installed Claude Code (`claude -p` with streamed JSON output), which signs in itself, and reports say headless use on subscription plans draws from a separate monthly credit. Ship this bridge only after confirming on Anthropic's own documentation that this use is permitted. Until then, Claude users connect with an Anthropic API key, or use Claude Code or Claude Desktop as an external agent (B).

In bridge mode, the provider's runtime also has its own built-in tools, such as shell and file editing. The bridge starts it with those tools disabled, or restricted to the workspace where the runtime cannot disable them, so Barloom's grant remains the limit. The connection page states what each runtime allows.

## 3b. Enabling agent features, and the user's responsibility

**Agent features are strictly disabled by default, and the code enforces it.** While they are off:

- every agent endpoint returns `403 agents_disabled`;
- `barloom mcp` exits with a message that says how to enable them;
- the assistant panel, Connections, and Inbox pages show only an explanation and the enable button;
- no agent token is accepted, and no bridge or model connection starts.

The switch is a single setting in `.barloom/agents.json`, which agent tokens cannot write.

**Enabling** happens in the app (the Agents page), or with `barloom agents enable` in a terminal. Both show the same notice and require the user to type a confirmation, not just click. The acceptance is recorded with the notice's version and the time. A new notice version turns agent features off until it is accepted again.

**The notice** is written in plain language. It is shown in full before enabling and kept at `barloom/assets/agents/notice.md`. It covers:

- **Software as is.** Barloom is provided without warranty. Its authors and contributors are not liable for any loss, including trading losses, data loss, or account suspension, as far as the law and the project's license allow.
- **Not financial advice.** Nothing Barloom or a connected model produces is investment advice. Simulated results do not predict real results.
- **Your data and your provider.** When agent features are on, workspace content, including strategies, results, and anything the agent reads, is sent to the AI provider the user chose. That provider's terms and privacy policy govern it, not Barloom's. Barloom's authors never receive it.
- **Your accounts and their terms.** The user is responsible for complying with their AI provider's and broker's terms, including how subscriptions may be used, and for any charges.
- **AI can be wrong or manipulated.** Models make mistakes and can be manipulated by text they read. The user should review what the agent proposes before approving it. Barloom's limits reduce risk; they do not remove it.
- **Credentials.** The user keeps keys in their keychain or environment. They must not paste keys into chats, scripts, or workspace files.
- **Turning it off.** How to disable agent features, revoke connections, and delete conversations.

**Prerequisites before a public open-source release** (outside this plan's code):

- **Choose a license.** The repository has none today. MIT or Apache-2.0 both include the standard "as is" warranty disclaimer and limitation of liability; Apache-2.0 adds a patent grant.
- **Legal review.** Have a lawyer review the license choice, the notice, and the README disclaimer. That matters most before live trading ships. Disclaimers reduce exposure but cannot rule out every liability, and this plan is not legal advice.

## 4. Tool surface

Tools map onto existing endpoints. Names are verbs a model picks reliably. Each tool has a JSON schema, a one-paragraph description that states its risk tier, and examples.

| Group | Tools | Tier | Backed by |
| --- | --- | --- | --- |
| Orient | `workspace_overview`, `list_cells`, `get_cell`, `list_scripts`, `list_scenarios`, `list_experiments`, `read_handbook(topic)` | observe | `GET workspace`, `cells`, `scripts`, `arena`; tutorial `content.js` moved to a shared JSON file |
| Results | `cell_results`, `compare_cells`, `get_timeline(range)`, `suite_matrix`, `holdings` | observe | `analysis`, `timeline`, `suite-report`, `holdings`, with new summary modes |
| Author | `read_script`, `write_script`, `check_script`, `create_cell`, `update_cell`, `check_cell`, `duplicate_cell` | draft | `cell-*` commands; new script endpoints |
| Simulate | `generate_scenario`, `transform_scenario`, `run_static`, `run_suite`, `advance_feed`, `wait_for_job` | simulate | `POST jobs` |
| Propose | `propose_feed_deployment`, `propose_archive`, `propose_retire`, later `propose_live_deployment` | propose | new proposal queue (section 6) |
| Account | `audit_log(mine)`, `my_grant` | observe | new |

New backend pieces these require:

- **Script endpoints.**
  - `GET scripts/{key}` returns the source.
  - `POST commands script-write {key, source, base_sha256}` uses optimistic concurrency, so the agent cannot silently overwrite an edit the user made in their editor.
  - `script-check` parses the script, lists its strategy classes and parameters, applies the policy checks in section 7, and, if asked, runs a smoke test on a tiny built-in tape in the sandbox.
  - Agent writes are confined to the scripts folders, and by default to `strategies/agent/`. Editing the user's other scripts needs the `edit_user_scripts` grant flag.
- **Summary modes.** `analysis` and `suite-report` gain a `summary=1` form: headline metrics, the number of sessions, whether the data is synthetic, cost assumptions, and warnings (too few trades, a single scenario, results dominated by one session). The full series stays available but paginated.
- **Structured errors.** Each error carries a stable `code` (for example `cell_not_ready`, `script_not_found`, `feed_settings_changed`) and a `hint` that says what to do next. Models recover from these far better than from free text. The UI keeps showing the message.
- **Idempotency.** Job submissions accept `idempotency_key`, so a client that retries after a timeout does not run a suite twice.
- **A schema.** A generated `docs/api.schema.json` (endpoints, parameters, result shapes) serves as the single source for the MCP tool schemas and is checked in tests, so the tools and the API cannot drift.

## 5. Permissions

Each connection, whether an external MCP client, a direct model connection, or a bridge, has a **grant**, chosen in the app and stored in `.barloom/agents.json`, which the API never exposes to agent tokens.

| Tier | Allows | Default |
| --- | --- | --- |
| observe | All reads and the handbook | on |
| draft | Write scripts in the agent folder; create and edit cell drafts; duplicate | on |
| simulate | Static runs, suites, scenario generation and transforms, and Advance on experiments the agent created | on |
| propose | Submit proposals for anything consequential | on |
| manage | Archive, restore, or retire without a proposal; Advance any experiment | off |
| live | Reserved. It can only *propose* live deployments, never approve them | off; not offered until broker support exists |

Grant options also include budgets: maximum jobs per hour, maximum sessions simulated per day, and maximum cells created. These stop a looping agent from filling the disk. A **revoke** button cuts off a connection immediately, and a **pause all agents** switch stops every one.

Deleting is never a tool. Archiving is the agent's strongest destructive action, and the user can restore anything archived.

## 6. Proposals and the approval inbox

A consequential action is a **proposal**: a stored request containing the action, its parameters, the agent's stated rationale, and the evidence it cites (job ids, result summaries). It appears in a new **Inbox** page and as a badge in the sidebar.

- The user sees exactly what will happen, as a rendered diff for cell versions and the scripts involved with their hashes. They approve, reject, or reject with a note the agent can read. Approval runs the action as the user, through the normal job path.
- Approval happens only in the browser app, which holds the browser token. No agent token can approve, so an agent manipulated by injected text can at most queue a request that a human must read.
- The assistant runs in that same browser, so the separation must also hold within the page.
  - Assistant tool calls run on the server under the connection's agent token, never the browser token.
  - Chat messages render as text and Barloom components only, never as raw HTML, so a reply cannot draw a button that looks like approval.
  - Approving requires opening the Inbox page and confirming there.
- A proposal pins the cell version and script hashes it was made against. If they change before approval, it is marked stale and cannot be approved.
- The agent can poll its proposals with `list_proposals`, so a workflow can continue after approval.

## 7. Running code the agent wrote

**This is the largest risk in the plan.** Barloom runs strategy scripts in its own process with the user's privileges (`engine.py` `exec`s them). Today that is acceptable because the user wrote or chose the code. Agent-written code needs more care, because a confused or manipulated agent could write a script that reads files, opens network connections, or deletes things the moment a simulation runs.

**Rule: no safety property depends on the model behaving, or on the sandbox alone.** A jailbroken or manipulated model can say or write anything, so every limit is a check in Barloom's code. That code runs whatever the model asked for, and the check refuses the request no matter how it is worded. The sandbox is one layer among several, so a sandbox escape alone does not reach deployment, secrets, or approvals.

Where the code enforces it:

| Check | Enforced in | Holds even if |
| --- | --- | --- |
| Agent features off unless enabled | Request routing, before any handler runs | The model or a script asks for anything |
| Grant tier and budgets per token | One authorization function that every agent request passes; there are no per-tool exceptions | A tool's description is misleading, or a model calls tools in an unexpected order |
| Approval only with the browser token | The proposal endpoint, which refuses agent and bridge tokens | The chat page is manipulated |
| Unreviewed code never runs in the server process | The strategy loader in `engine.py`. Before running any script, it checks the review state of the script's hash, and runs `agent-unreviewed` code only when called from the sandbox runner | A new code path forgets to use the sandbox |
| Unreviewed code never deploys | `Deployer.feed` (and the future live path) checks every script hash | A proposal was crafted to look reviewed |
| Agents cannot write grants, notices, review states, risk limits, or `.barloom/` | Path checks in the script-write and command handlers, refusing those paths for agent tokens | The model is told those files are scripts |
| Secrets never leave | Environment stripping at sandbox start, and output redaction of known key patterns in tool results and the audit log | A script or model tries to print them |

Each row has tests that call the check directly, bypassing the tools, and confirm it refuses. That way a regression in one layer fails a test even when the other layers would have caught the problem.

The layers for running agent code:

1. **Provenance.** Every script carries a review state keyed by its content hash: `user` (on disk before agents, or saved outside Barloom), `agent-unreviewed`, or `reviewed` (a user approved that exact hash in the app). The app marks agent-written and unreviewed scripts on cell cards and in the script picker.
2. **A sandboxed runner for unreviewed code.**
   - Simulations whose cells use unreviewed scripts run in a separate worker subprocess, not the server process:
     - the working directory is a temporary folder;
     - inputs are passed over a pipe;
     - environment variables are stripped, so no `APCA_*` or other secrets reach it;
     - CPU time and memory are limited (Job Objects on Windows, `resource` limits on POSIX);
     - there is a wall-clock timeout.
   - Before running, `script-check` applies an AST policy: an import allowlist (`math`, `statistics`, `collections`, `itertools`, `dataclasses`, `typing`, `functools`, `datetime`, `random`, plus `numpy` if installed); no `open`, `exec`, `eval`, `__import__`, or `compile`; no dunder attribute access; no `globals` or `getattr` with computed names.
   - Inside the child process, a Python audit hook (`sys.addaudithook`), installed before the strategy is loaded, refuses file opens outside the inputs, socket creation, subprocess and `os.system` calls, and imports outside the allowlist. This catches what the static AST check cannot see, such as code that builds names at runtime.
   - **Limits, stated honestly.** An AST policy and a subprocess are not a security boundary against a determined attacker who controls the code. They do stop the realistic failures: a mistaken agent, or an injected instruction to read `~/.ssh` or call out to a URL. A container- or WASM-based runner can replace the subprocess later behind the same interface.
3. **Review gates deployment.** Feed deployment, and later live deployment, requires every script the cell uses to be `user` or `reviewed`. The proposal view shows the script source for review, and approving the proposal reviews those hashes. Unreviewed code can therefore be simulated in the sandbox, but never run unattended.

## 8. Research hygiene

An agent can try hundreds of variants in minutes, which is exactly how backtests overfit. Barloom can make this visible instead of leaving it to the model's discipline:

- **Attempt counting.** Each agent session records how many cell versions and parameter sets it evaluated. Result summaries and proposals show the count, for example "best of 140 variants", and warn when it is large compared to the data.
- **Sealed holdout scenarios.** The user can mark scenarios as holdout. Agents cannot see their data or per-scenario results. They can only request a holdout evaluation as part of a proposal, and it runs once per cell version. This is the agent equivalent of a test set.
- **Forward test as the gate.** The suggested workflow, written into the handbook and the tool descriptions, is: draft, simulate, propose Feed, forward-test on sessions the agent never saw, then (later) propose live. Feed's pinned hashes and through-dates already make that forward test honest.
- **Caveats in summaries.** Synthetic data, missing costs, or single-scenario results are stated in the summary itself, so they reach the model and not just the UI.

## 9. Toward live trading

Nothing here sends orders in v0.3.0. The live tier is reserved so that the future broker work slots into an existing safety model, not the other way round. When live trading lands, it will follow these rules:

- Barloom-owned **risk limits** per cell and per account: maximum position, maximum order notional, daily loss stop, and allowed symbols. Only the user sets them, in the app. Agents can read them but not change them.
- A **kill switch** in the app and in the CLI flattens or halts all live cells. It works even if every agent connection is compromised.
- **Live deployment always needs a proposal approved in the app**, regardless of grant, with a confirmation that shows the risk limits and the forward-test record.
- Broker credentials stay in environment variables (`APCA_API_KEY_ID`/`APCA_API_SECRET_KEY`). No tool returns them, they never pass to the sandbox, and the audit log redacts them.

## 10. Audit and visibility

- `.barloom/agent-log.sqlite` records every agent call: time, connection, tool, parameters (with secrets redacted), outcome, job id, and duration. It is append-only from the API's side.
- **Activity** gains an agent filter and a live "agent is working" indicator. Cell versions and scripts record their author (`user` or a connection name), and cards show a small agent mark.
- The agent can read its own log (`audit_log(mine)`), which helps it resume work in a new conversation.

## 11. Prompt-injection handling

- Tool results wrap text from the workspace (names, descriptions, script comments, CSV headers) in a labelled field, `untrusted_text`. The MCP server's instructions tell the agent such text is data. This lowers risk but does not remove it, which is why sections 5–7 do not depend on it.
- The agent has no network fetch tool and no shell tool. Importing outside data stays a user action in the CLI.
- An injection fixture suite runs in tests: scenario descriptions and script comments that contain instructions. The tests assert that no tool sequence open to an agent token can approve a proposal, change a grant, read a secret, or run unreviewed code outside the sandbox.

## 13. Testing

- **Contract tests.** Every MCP tool is called against a temporary workspace through a real server, and results are validated against the schema.
- **Disabled by default.** On a fresh workspace, every agent endpoint, `barloom mcp`, and every connection kind is refused. The same holds again after a new notice version, until the notice is accepted.
- **Permission matrix.** For each tier and each tool or endpoint, a test checks it is allowed or refused, including that agent tokens are refused on approval, grant, and kill-switch endpoints.
- **Enforcement without the sandbox.** Each check in the section 7 table is called directly, without the tools or the sandbox in front of it, and must refuse. One example: calling the strategy loader on an `agent-unreviewed` hash outside the sandbox runner.
- **Sandbox tests.** Scripts that try to `open` a file, import `socket` or `os`, loop forever, or allocate without bound are rejected by the check or killed by the runner. The parent environment's secrets are absent in the child.
- **Parity between A and B.** The same scripted tool sequence runs through `barloom mcp`, a direct connection with a fake model adapter that replays recorded tool calls, and a fake bridge runtime. The tests assert identical workspace results, audit entries, and refusals.
- **Adapter tests.** Recorded streaming responses from each provider format (including tool-call fragments split across chunks, and refusals) are translated into the internal event stream. No test calls a real provider, and no test needs a key.
- **Scripted agent scenarios.** Deterministic sequences of tool calls (draft, check, simulate, propose, approve in the app, Feed) run as tests. A few real-model evaluation tasks are run by hand before release ("improve this cell's drawdown without raising variant count past 50"), and their transcripts are kept under `docs/agent-evals/`.

## 15. As built

All 17 parts shipped in v0.3.0. Where the build differs from the text above:

- **The notice and settings.** The notice ships in the package (`barloom/assets/agents/notice.md`). Agent settings, connections, and the review list live on an **Agents** page rather than under Settings.
- **Tokens are stored only as digests.** Clients get theirs through `BARLOOM_TOKEN`. Bridges get a fresh token for each turn, withdrawn when the turn ends.
- **Untrusted text.** Every MCP tool result carries a second text item reminding the model that workspace text is data, and the assistant's system prompt says the same. Results are not wrapped field by field in an `untrusted_text` field. As planned, no limit depends on either.
- **The sandbox** runs one child process per unreviewed strategy. The child uses the base interpreter, because a Windows venv launcher starts a second process, which the one-process limit forbids.
- **Holdout tests** run through a `holdout-test` proposal, once per cell settings fingerprint.
- **The Codex bridge** uses `codex exec --json`. Codex 0.157 cannot disable its command runner (`unified_exec`), so Barloom stops a turn when Codex starts a command (ADR-0020).
- **Security review:** see `docs/security-review-v0.3.0.md` for the findings fixed before release and the accepted risks.
- **Still to do by hand:** testing `barloom mcp` with Claude Code, Claude Desktop, and the Codex CLI, and a real Codex bridge turn on a ChatGPT plan. Neither can be automated without the user's accounts.
- **Deferred:** the Claude Code bridge (until Anthropic's terms are confirmed), local models and other providers, streaming replies, and a per-day budget on simulated sessions.
