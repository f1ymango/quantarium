# Plan: v0.6.x — The referee

- **Status:** Done: v0.6.0 to v0.6.5 (2026-10-25)
- **Date:** 2026-10-25
- **Roadmap:** [roadmap to v1.0](roadmap-to-v1.md), v0.6. **Decision record:** [ADR-0037](../adr/0037-referee-not-competitor.md)

## 1. Goal

Judge trading decisions made **outside** Barloom: by another framework, by a language-model trading agent, by a spreadsheet, or by hand. Barloom replays those decisions on its own engine, with its own costs, portfolio controls, and Lab rules. Other systems hand over **decisions, not returns**, so they cannot report their own fills.

## 2. The central problem: hindsight

A file of past decisions may have been written after the fact, with knowledge of what happened next. Barloom cannot tell a genuine record from a hindsight one. Neither can anyone else who only sees the file. The plan therefore separates three ways decisions can reach Barloom, by how much they can prove:

| Way in | How decisions arrive | What it can prove | Highest Lab verdict |
| --- | --- | --- | --- |
| **Rescore** | A finished decision file | Nothing about hindsight. Real costs, controls, drawdown, and turnover are still worth seeing | `unknown`, always with the reason "decisions supplied after the fact" |
| **Forward** | Each session's decision is submitted before that session's prices exist; Barloom stamps when it arrived | That no decision used later prices | Every verdict, over the forward period only |
| **Live** | Barloom runs the outside program step by step and shows it only the data up to each session | No look-ahead through Barloom. On synthetic or disguised markets, nothing to look up elsewhere either | Every verdict, under the same rules as model-driven cells (training cutoffs, synthetic and disguised markets) |

Rescoring is still useful: it shows what a strategy looks like after realistic costs and next to simple controls. It is labelled as exploratory, and never as evidence.

## 4. The decision file

JSON is the exact format; CSV is accepted for people who keep decisions in a spreadsheet.

```json
{
  "format": "barloom-decisions-v1",
  "source": {"system": "my-agent", "version": "0.3", "model": "example-model", "training_cutoff": "2025-01-31"},
  "symbols": ["AAA", "BBB"],
  "decisions": [
    {"date": "2030-01-07", "weights": {"AAA": 0.5, "BBB": 0.3}, "note": "trend up"},
    {"date": "2030-01-08", "weights": null}
  ]
}
```

```csv
date,symbol,weight
2030-01-07,AAA,0.5
2030-01-07,BBB,0.3
```

- A decision is made at the close of `date`, using information through that close, and fills at the next open. This matches Barloom's own strategies.
- `weights: null` keeps the current holdings. A date with no entry also keeps them.
- Weights follow the existing rules: from 0 to 1 each, totalling at most 1, long-only. Orders (`market`, `limit`, `stop`) are accepted in the same shape as a script's `Decision`.
- `source` is self-declared and shown in reports; Barloom does not verify it.
- Limits: at most 50,000 decisions and 500 symbols per file, and 10 MB. Notes are plain text, kept at most 500 characters, and shown as text.

## 5. Security

The referee adds three kinds of untrusted input. Each gets misuse tests in `tests/security/`.

- **Decision files are data, not code.** The reader is strict and bounded, refuses `NaN` and infinities, and is fuzzed like the v0.5 parsers. Paths follow the workspace path rules.
- **Submissions in the forward inbox** come from agents or outside programs through the existing checkpoint. Agents need the simulate tier and a budget. The inbox is append-only; nobody, including the browser, can change a stamped submission.
- **Deciders are outside programs** the user chose to run, as with agent apps. Only the user can register one, in the browser. An agent cannot. A decider:
  - starts in an empty folder;
  - gets an environment without Barloom's, broker, and GitHub secrets, plus only the variables the user names for it (for example its own model key);
  - runs with per-session and per-run time limits, and a size limit on its replies;
  - receives only data up to the current session.

  Barloom cannot stop a decider from reading the internet. So on real history, a decider is judged like a model-driven cell: real data only after its declared training cutoff, otherwise synthetic and disguised markets.

## 6. Out of scope

- Importing other engines' results (returns, fills, or equity curves). Only decisions are accepted.
- Running other frameworks inside Barloom. They run as deciders in their own process, or export files.
- Real orders.

## 7. Decisions

Made with the maintainer on 2026-10-25:

1. **Rescored verdicts are capped at `unknown`**, with the reason shown.
2. **Forward decisions** may be submitted by agents with the simulate tier and a budget, through the checkpoint, and by the browser.
3. **Deciders** get an environment without secrets, plus only the variables the user names for them.
4. **CSV is accepted** as well as JSON, for weights only.

## 8. As built

### v0.6.0 — Decision files

- `barloom/decisions.py`: `load_decisions` and `parse_decisions` return a `DecisionFile` (source, symbols, decisions by date, SHA-256, kind). `DecisionFile.entry(day)` gives that close's `DecisionEntry` (weights or None, orders or None, note), or None when the file has no decision for the day.
- JSON is checked strictly: the format name, known fields only, listed and unique symbols, ISO dates, at most one decision per date, weights from 0 to 1 totalling at most 1, orders with a valid side, kind, positive whole shares, and a positive price, and notes and tags of plain text. CSV must have exactly `date,symbol,weight`; one row per symbol and date.
- `barloom/strictjson.py` holds the strict JSON reader (no `NaN`, no infinities, nesting limit) that `server.py` used privately; request bodies and decision files both use it.
- `barloom decisions check` prints the summary.
- Tests: `tests/test_decisions.py`. `tests/security/test_decision_files.py` fuzzes JSON and CSV files with seeded mutations and hostile strings; the reader may raise only `ValueError`, and everything it accepts satisfies the rules. A deeper run (seed 11, 800 mutations per format) found nothing. The JSON and CSV mutation helpers moved into the harness.

### v0.6.1 — Rescoring

- A sleeve `{"decisions": "<workspace key>"}` replaces scripts. `Library._decision_problems` checks it (one file, inside a `decisions` folder, valid, symbols held by the cell, no scripts, allocator, model access, or risk card, rebalance interval 1) and adds the built-in strategy `barloom.referee:ReplayDecisions` with the file's absolute path, SHA-256, and, for a Simple cell, its symbol. The engine needed no change: the strategy returns a `Decision`, holding when the file has no entry for the day.
- A cell that loads no script reports the workspace root as its strategy folder.
- `Workspace.folders` gains `decisions` (default `decisions/`), and the overview lists each file's summary or error.
- The Lab refused decision cells until v0.6.2.
- App: the Configure tab chooses between scripts and a decision file, shows the file's summary, and labels the sleeve on the Overview. Checked in the browser on a scratch workspace: the choice, the summary, saving, a suite run, and the chart's trades.

### v0.6.2 — The Lab for decisions

- `Lab._snapshot` pins each decision file (`decision_files`: SHA-256, first and last date) and marks the registration `decisions: after_the_fact`. `_verify` makes the experiment stale when a pinned file changes.
- `Lab._verdict` caps such a result at `unknown`, with a caveat explaining hindsight, and names scenarios outside the file's dates. The controls and the matrix are computed as for any candidate.
- Disguised replays are refused for decision files, whose dates are fixed.
- The forward referee (v0.6.3) will be the first way for outside decisions to earn a full verdict.

### v0.6.3 — Forward referee

- `barloom/inbox.py`: `create`, `submit`, `read`, `pin`, `summary`, `inboxes`. The deadline for a decision dated D is the next NYSE session's 09:30 New York open (`market_calendar.sessions`). Arrival is Barloom's clock at submission; `on_time` is recomputed on every read rather than trusted from the file.
- `barloom.referee:ReplayInbox` replays on-time decisions; with `until_bytes` and `sha256` it reads only the frozen prefix and refuses a rewritten one.
- Cells take `{"inbox": name}` sleeves; the inbox's declared symbols must be held by the cell.
- The Lab freezes inboxes at registration (`inboxes`: bytes, SHA-256, first and last on-time date, late count; `decisions: forward`), compares the cell without the freeze (`_unfrozen`), refuses non-historical scenarios and disguised replays, and adds caveats for late decisions and early scenario starts. Verdicts are not capped.
- One subtlety found while designing it: on a synthetic or future-dated scenario the "future" prices already exist in the workspace, so a clock-based deadline proves nothing there. Hence the real-prices rule.
- App: the Configure tab lists forward inboxes beside decision files, with on-time and late counts. Checked in the browser.

### v0.6.4 — Live referee

- `barloom/deciders.py`: the registry (`.barloom/deciders.json`; `create`, `delete`, `listing`, `fingerprint`) and `DeciderProcess`, which starts the command in an empty temporary folder with `BASE_ENV` plus the named variables, sends `init` and one `session` message per close (new history rows only, as the sandbox does), validates each reply with the decision-file rules, and appends it to a tape. Timeouts: 60 seconds to start, 120 per session; replies are limited to 1 MB.
- `barloom.referee:LiveDecider` is the engine strategy; with a `fingerprint` it refuses a decider changed since registration.
- Tapes (`barloom-decision-tape-v1`, `.jsonl`) are read by `load_decisions`, and the workspace lists them with other decision files.
- Agents: `decider-create` and `decider-delete` are browser-only; `GET deciders` is not an agent route; `Api._refuse_agent_deciders` refuses agent jobs whose cells or config name a decider; agents cannot save a cell with one.
- The Lab pins `decider` (name, cutoff, fingerprint), marks `decisions: live`, and reuses the model-contamination rules with the decider's cutoff. Disguised replays are allowed.
- Not done: the decider's own child processes are not stopped with it, only the program Barloom started. Registration has no form in the app yet (the CLI and the API command do it); v0.6.5 adds one.
- Checked in the browser: choosing a decider on the Configure tab, saving, and running a suite through the server.

### v0.6.5 — Examples and the app

- `NewSource` in the Configure tab's decision panel opens an inbox for the cell's symbols and registers a decider through the browser-only `decider-create` command, then reloads the lists.
- Handbook chapter 14 (`referee`) with topics `referee`, `decision-files`, `forward-inbox`, `deciders`, and feature rows; `tests/test_tutorial_content.py` checks the topics are covered.
- `examples/decisions/steady_bull_weekly.csv` (47 weekly decisions from a 20-session moving-average rule) and `examples/deciders/moving_average.py`; `tests/test_deciders.py` runs the decider and loads the file.
- `docs/referee.md`, linked from the README.
- Checked in the browser: the forms (a decider registered, its arguments split by line), the lists reloading, and the help button opening chapter 14.
