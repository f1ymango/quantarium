# Plan: v0.5.x — Security hardening

- **Status:** Released in v0.5.5 (2026-10-24)
- **Date:** 2026-10-24
- **Scope:** Defensive security testing of Quantarium's own code. Find and fix weaknesses that ordinary tests miss, using misuse tests that run only inside Quantarium's test suite, against disposable workspaces. Nothing reaches the host computer's files, real accounts, other people's systems, or the network.

## 1. Approach

An AI agent with free rein to "attack the repository" on the maintainer's computer would put the computer, its credentials, and its accounts at risk. A finding is not worth that, and an unbounded exercise is also hard to repeat or verify.

Instead, every check in v0.5 is a **misuse test**: an automated test that uses Quantarium the way a careless or hostile user, agent, or file might, and checks that Quantarium refuses safely.

- It is written down, reviewed before it runs, and aimed at a disposable copy of Quantarium.
- It runs as part of the test suite, so it can be repeated after every change.
- Each finding becomes a regression test that fails before the fix and passes after it.

This is how the v0.3.0 security review worked (`docs/security-review-v0.3.0.md`): it found seven issues, including two of high severity, using probes run as a hostile agent against a test server. v0.5 makes that method systematic, and extends it to everything added since.

## 2. Rules of engagement

These rules apply to every agent working on v0.5, and to the maintainer's own tests. They add to `AGENTS.md`.

1. **Targets are Quantarium's code, running on loopback, in disposable workspaces.** That means temporary test folders, or `quantarium serve --fresh`, never the maintainer's own workspace.
2. **No real secrets anywhere in the exercise.**
   - Tests plant *canary* values: fake API keys, a fake broker key, and a fake SSH key and fake browser files in a fake home folder.
   - The tests then check that no canary ever appears in a response, a log, a journal, a tape, an error, or a file written outside its folder.
   - Real keys and sign-ins stay out of the test process's environment.
3. **No network beyond loopback.**
   - Model APIs, agent apps, and market data are fakes (as in `tests/fake_acp.py` and `tests/fake_claude.py`), or the local Ollama server.
   - No test contacts a third-party service or a real account.
4. **Nothing outside the test's temporary folder is written, changed, or deleted.** Each test checks this for its own folder tree.
5. **Sandbox tests verify Quantarium's own rules.** A test script does something Quantarium's sandbox policy forbids, such as opening a canary file, importing a refused module, or opening a socket, and the test checks that Quantarium refuses it. These tests do not search for new ways around Python's or the operating system's protections (see Out of scope).
6. **Findings stay private until fixed.** The repository is private. If it goes public, findings are fixed before their details are published.
7. **The maintainer approves each phase.** Installing new tools or widening the scope needs the maintainer's approval in chat.

### Out of scope

v0.5 is defensive testing of Quantarium's own code. It does not include:

- **Exploit research on other software:** Python, the operating system, browsers, or any library. Quantarium does not depend on its sandbox being a hard boundary against attacks on Python itself (ADR-0016), and Feed and Live never run unreviewed code.
- **Malware-like behaviour of any kind:** code that persists, spreads, hides from or disables security software, or captures data beyond the planted canaries.
- **Anything outside Quantarium running in a test:** other programs, other people's systems, real accounts, real credentials, or third-party services.
- **Load tests beyond bounded local checks:** for example, a slow client against a local test server with a time limit.

## 3. Test environment

All v0.5 work runs in the normal test suite:

- temporary workspaces, and a fake home folder with canaries;
- fake model, agent, and market services;
- loopback only.

It covers every area in section 4. No separate machine is needed, because no test does anything that would be harmful if one of Quantarium's boundaries failed. The worst outcome of a failing test is a failing test.

## 4. Attack surface

Taken from the security invariants in `AGENTS.md` and the features added since v0.3.0:

| Area | What the misuse tests check |
| --- | --- |
| Browser boundary (`server.py`) | Cross-site requests, a rebound DNS name, malformed requests, oversized bodies, slow clients |
| Agent checkpoint (`api.py`, `agents.py`) | Reaching operations beyond a connection's tier; slipping past path, holdout, and budget rules through nested parameters, proposals, or rarely used routes |
| MCP (`mcp.py`) | Tool arguments that the schema allows but the server mishandles |
| Sandbox and provenance | Agent-written code running outside the sandbox; getting a script marked reviewed; using a reviewed script's name or hash to smuggle in another |
| Model and agent apps (`providers*.py`, `runtimes/`) | Keys sent to the wrong host; a fake agent app that misbehaves, such as using unannounced tools, sending floods, or returning malformed data |
| The `ask` gateway and tapes | Answers crafted to steer a strategy; budget bypass; a tampered tape; a grant that outlives its script |
| The Lab | Verdicts that flatter a candidate: a tampered ledger, reused data, stale pins, contamination labels that miss |
| Files and parsers | Malformed or hostile scenarios, CSVs, model cards, configs, cell files, and workspace settings |
| Pages (`assets/app/`) | Model, agent, and file text that renders as markup |
| Supply chain | Dependencies, the build backend, and workflows (`tests/test_repository_policy.py`) |

## 5. Methods

1. **Boundary review.** For each area, read the code path against the threat model and write down what would have to go wrong. Then probe each suspicion with a test (the v0.3.0 method).
2. **Hostile fixtures.** Reusable fakes that behave badly on purpose:
   - an agent connection with every tier;
   - a model that returns crafted answers;
   - an agent app that ignores its instructions;
   - scenario and data files with hostile content;
   - scripts that try to cross the sandbox's boundary harmlessly.
3. **Fuzzing with the standard library.** Seeded, time-limited random inputs for API parameters, file parsers, and schemas, checking that Quantarium refuses cleanly and never crashes a server thread, leaks a canary, or writes outside its folder. Seeds make every failure reproducible.
4. **Canary checks.** Every test in the security suite ends by searching what Quantarium produced for the planted canaries.
5. **Static checks.**
   - Tests flag dangerous patterns in Quantarium's own code: `eval`, `exec`, `pickle`, `subprocess` with a shell, raw-HTML sinks, and unchecked paths.
   - Established scanners (for example `bandit` for code and `pip-audit` for dependencies) would add coverage, but installing them needs the maintainer's approval under `AGENTS.md`.
6. **A second reviewer.** Another agent, such as Codex, reviews the same scope independently, and the two sets of findings are compared. Neither agent fixes the other's findings unreviewed.

## 8. As built

### v0.5.0 — The security harness

- `tests/security/harness.py`:
  - `Canaries` writes fake secrets into a fake home and patches the environment (`HOME`, `USERPROFILE`, model, broker, and GitHub keys), and finds them again in text or in any workspace file's bytes.
  - `FolderGuard` snapshots folders and reports additions, changes, and removals.
  - `MisuseCase` runs a server on a temporary workspace with an every-tier agent connection, records every response, and in `tearDown` fails on any canary in a response or workspace file, or any change outside the workspace.
  - `Fuzzer` gives seeded hostile values: traversal paths, `.quantarium` paths, the sentinel's absolute path, Windows reserved names, NUL, long, bidirectional, and markup strings, extreme numbers, and nested lists and objects.
- `tests/security/test_harness.py` checks that the harness itself notices planted leaks and folder changes, and that the fuzzer replays from its seed.
- `tests/security/test_static_patterns.py` holds the allowlist of risky Python patterns with their reasons, and checks pages for raw-HTML and code-from-text sinks.
- Found while building it, for v0.5.1: the server sets no socket timeout, so a slow client can hold a handler thread indefinitely.
- Added in v0.5.1: `NetworkGuard`, which blocks non-loopback connections and name lookups in the test process, and an in-memory `keyring` stand-in.

### v0.5.1 — Requests and permissions

Tests: `tests/security/test_requests.py`, `test_permissions.py`, `test_mcp.py`. Default fuzzing is 6 rounds per operation from seed 2026; `QUANTARIUM_FUZZ_SEED` and `QUANTARIUM_FUZZ_ROUNDS` explore further.

| Finding | Severity | Fix |
| --- | --- | --- |
| No socket timeout: a stalled client holds a server thread | Medium (local denial of service) | `Handler.timeout = REQUEST_TIMEOUT` (30 s) |
| Deeply nested JSON raised `RecursionError`, returned 500 | Low | Parse errors map to 400; bodies deeper than `MAX_DEPTH` (64) are refused |
| `NaN`, `Infinity`, and overflowing numbers accepted in bodies | Low (bound checks pass `NaN`) | `parse_constant` and `parse_float` refuse them |
| Non-text cell names crashed `cell-create` and `cell-save` | Low | `cells._check_name`: text, at most 200 characters, no control characters |
| Non-object `spec` crashed the agent check in `cell-save` | Low (failed closed) | 400 before the check |
| Deploy costs checked only inside the job, after a config was written | Low | Checked at submit with the config's own rule |
| A malformed MCP message ended the stdio session | Low | Type checks in `tools/call`; `serve_stdio` answers any failure with a JSON-RPC error |

Checked and sound: tier checks across route spellings, browser-only routes, token handling, every path parameter against hidden and outside paths, and holdout refusal across fourteen path spellings (case, separators, trailing dots, `..`, absolute paths, and files inside the scenario). The Lab compares manifests, so it also refuses a holdout under any path.

### v0.5.2 — Code execution

Tests: `tests/security/test_code_execution.py`. Each test runs harmless scripts (they return a weight) and detects an in-process load through `sys.modules`.

| Finding | Severity | Fix |
| --- | --- | --- |
| Agent script paths with `./`, `//`, or other capitals were recorded under one key and checked under another, so the script ran in-process as the user's | High: default-tier agents ran code in the server process | `script_files` records `workspace.key(path)`; `provenance.same_key` normalizes separators, `.` and `..`, and case on Windows |
| A reviewed script's imports were not checked; an unreviewed helper ran in-process | High (needs one review of the importing script) | `provenance._ImportGuard`, a `sys.meta_path` finder installed by `engine`, refuses unreviewed agent files on every import. Python's own folders and Quantarium's package are skipped |
| A strategy's folder stayed first on `sys.path` after loading | Medium (shadows later imports in the server) | `engine._importable` adds the folder only while the strategy loads |
| `script-write` applied path rules to source code | Low (usability) | `source` is exempt for `script-write` and `script-check` |

Checked and sound: the sandbox refuses canary file reads, `os` and `socket` imports, and dunder access; agents cannot write `.pth`, `.pyc`, `.pyw`, package, `sitecustomize`, hidden, or outside files; model card paths follow the path rules; agent-written allocators load through the same checks as strategies.

Accepted: with `edit_user_scripts`, an agent may write `strategies/sitecustomize.py`. Python reads `sitecustomize` only at start-up from its own path, and the file is still unreviewed, so the import guard refuses it.

The import guard costs no measurable time: three heavy test modules took 46 to 48 seconds with it and 49 without.

### v0.5.3 — Files and data

Tests: `tests/security/test_files.py` and `test_lab_integrity.py`. The parser fuzzing runs 60 mutations per parser by default (ten times `QUANTARIUM_FUZZ_ROUNDS`); a deeper run with seed 7 and 30 rounds found nothing further.

| Finding | Severity | Fix |
| --- | --- | --- |
| Identical prices under a new scenario name or folder counted as fresh data in the Lab | Medium (flatters a verdict) | `lab._data_names` matches reuse on family and on `prices_sha256`; shared prices within one experiment get the independence caveat |
| `NaN`, negative, or non-numeric amounts in a tape switched the cost budget off or broke the summary | Low (tapes live in `.quantarium`, out of agents' reach) | `ask._amount`: the gateway refuses such a tape; `tape_summary` skips damaged entries |
| Short CSV rows raised `AttributeError` | Low | `data.load_daily_csv` and `load_actions_csv` refuse rows with too few columns |
| Infinite values in vendor CSVs raised `OverflowError` | Low | `importer._number` requires finite numbers |
| Configs and suites with wrongly typed entries raised `AttributeError` | Low | `config.plain_errors` reports structural errors in `load_config`, `load_feed_config`, `load_live_config`, and `load_suite` as `ValueError` |

Checked and sound: scenario manifests (hash checks stop tampered files), risk cards (content-addressed, every field validated), damaged cells, scenarios, scripts, and databases in reads; agent settings fail closed (agents refused) when damaged; unreadable provenance stops agent scripts from running as the user's own; damaged Lab and proposal ledgers give 4xx errors.

Out of scope: someone who can edit files in `.quantarium` is the user, or has the user's access. Integrity there protects against damage and agents, not against the user.

### v0.5.4 — Models and agent apps

Tests: `tests/security/test_models_and_apps.py`, with `tests/security/hostile_acp.py` as a misbehaving agent app, and `HostileModel` as a model API. Neither contacts anything but the test process.

| Finding | Severity | Fix |
| --- | --- | --- |
| Agent apps received secrets whose names the short denylist missed (`GITHUB_TOKEN`, `AWS_SECRET_ACCESS_KEY`, ...) | Medium (breaks "no secrets in their environment") | `runtimes.SECRET_WORDS`, longer `SECRET_PREFIXES` and `SECRET_SUFFIXES` |
| A non-command tool whose title contained a Quantarium tool name got permission | Medium (needs an agent app that does not mark shell tools as `execute`) | `acp.quantarium_tool` requires the whole title to name the tool, with at most a plain parenthetical note |
| Non-numeric or `NaN` usage raised before the call was counted, so the call budget never ran out | Medium (a misbehaving or hostile model API) | `ask._reported`; unreported output counts as `max_output_tokens` |
| `*.localhost` names counted as loopback for plain HTTP | Low | `presets.is_loopback` accepts `localhost` and loopback addresses only |
| A flood of text was kept in full; malformed updates or requests ended the turn with an exception | Low | `acp.MAX_TURN_TEXT`, `MAX_TURN_CALLS`, type checks, `acp._count` |

Checked and sound: endpoints with user names, fragments, queries, odd schemes, embedded whitespace, or a loopback name inside another host are refused; crafted answers (out of range, wrong type, `NaN`, extra fields, Markdown fences, arrays) never pass the schema; file and terminal requests from agent apps are refused; agent apps start in an empty folder; pages render model and agent text as text, and every link built from data is an in-app route.

Covered elsewhere: redirects. `tests/test_providers.py` (`test_a_redirect_is_never_followed_with_the_key`) runs a local server that answers 307 towards a second local server, and checks that the second one receives nothing. It needs the `[assistant]` extra, so it runs in that environment.

### v0.5.5 — Report

`docs/security-review-v0.5.md` collects the findings of v0.5.1 to v0.5.4 (G1 to G18), what was checked and held, accepted risks, and what remains untested. While writing it, the code execution tests gained Windows path forms: alternate data streams, short 8.3 names, and device names are refused. Windows 11 treats `con.py` as an ordinary file, which provenance records like any other.

The suite now has 50 tests in `tests/security/`, and runs in the normal `py -m unittest discover -s tests`.
